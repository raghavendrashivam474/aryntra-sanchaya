## 1. Executive Summary



Sanchaya v0.6.0 was a **document metadata vault**. It stored *information about* documents — titles, categories, issuers, expiry dates — but it never stored the actual documents themselves.



v0.7.0 transforms Sanchaya into an **artifact vault**. Users can now attach, open, replace, and remove the actual PDF or image file associated with each document record. The physical files are stored in a Sanchaya-managed directory under the operating system's application data path. The architecture introduced no new frameworks, no ORM, no cloud services. It extended the existing clean-architecture pattern with a new domain entity, new repository, new storage abstraction, new use cases, and new thin Tauri commands.



The transition was completed with **zero regressions** to the existing 79-test foundation.

&#x20;   document_id       TEXT NOT NULL

- `documents.file_path` column left in place as a legacy nullable field. Not removed to avoid migration risk.

## 5. Problems Encountered and How They Were Resolved



### Problem 1: Tauri v2 Capability Permission Names



**Symptom:** Build failed during the Tauri build-script phase with:



```text

Permission fs:allow-create-dir not found

Permission fs:scope-app-data-recursive not found

```



**Root Cause:** Tauri v2 changed the capability permission identifiers from the documentation that was referenced. The correct names were different from what was initially used.



Wrong names used:

```text

fs:allow-create-dir

fs:allow-remove-file

fs:scope-app-data-recursive

```



Correct names from the Tauri permission registry:

```text

fs:allow-mkdir

fs:allow-remove

fs:scope-appdata-recursive

```



**Resolution:** The capability names were corrected by reading the full list of valid permissions from the build error output itself, which includes every available permission identifier.



**Lesson:** Tauri v2 capability names cannot be guessed. The build script's error output is the authoritative reference for valid permission identifiers.



---



### Problem 2: Non-UTF-8 Bytes in Rust Source Files



**Symptom:** Cargo refused to compile with:



```text

error: couldn't read `src\\application\\attach_file.rs`:

&#x20;      stream did not contain valid UTF-8

note: byte `151` is not valid utf-8

```



The offending byte was in a comment containing an em-dash character.



**Root Cause:** PowerShell's `Set-Content` and here-string (`@' ... '@`) mechanism silently converts certain Unicode characters to Windows-1252 encoding when writing files. The em-dash character (U+2014) was encoded as byte 0x97 (151 decimal) in Windows-1252, which is not valid UTF-8.



**Affected files:** 5 of 7 newly created Rust files contained at least one non-ASCII byte.



**Resolution (attempt 1):** Used `[System.IO.File]::WriteAllText()` with `[System.Text.Encoding]::UTF8` to read and rewrite each file, replacing non-ASCII bytes with hyphens using regex. This still injected a BOM (byte order mark, 3 bytes: 0xEF 0xBB 0xBF) at the start of files.



**Resolution (attempt 2 — successful):** Used `[System.IO.File]::ReadAllBytes()` and `WriteAllBytes()` to work at the raw byte level, replacing every byte > 127 with byte 45 (ASCII hyphen):



```powershell

$bytes = [System.IO.File]::ReadAllBytes($full)

$cleaned = $bytes | ForEach-Object { if ($_ -gt 127) { 45 } else { $_ } }

[System.IO.File]::WriteAllBytes($full, [byte[]]$cleaned)

```



This eliminated all non-ASCII bytes including BOM artifacts.



**Lesson:** When writing Rust source files from PowerShell, never use `Set-Content` for anything containing Unicode. Use `[System.Text.Encoding]::UTF8.GetBytes()` to produce BOM-free UTF-8 bytes, then `WriteAllBytes()` to write them. Alternatively, ensure all comments contain only ASCII characters.

### Problem 3: Triple-Dash Frontmatter Error



**Symptom:** After the byte-scrubbing fix, Cargo produced a new error:



```text

error: invalid infostring for frontmatter

&#x20; --> src\\application\\attach_file.rs:1:4

&#x20;  |

&#x20;1 | ---// application/attach_file.rs

error: frontmatters are experimental

```



**Root Cause:** The em-dash character (3 bytes in UTF-8: 0xE2 0x80 0x94) was at the start of a comment line. When each of those 3 bytes was replaced with a hyphen, the result was `---` at the very beginning of the file. The Rust compiler interpreted `---` at line 1 as a frontmatter delimiter (an experimental feature per RFC #136889), causing a parse error.



**Affected files:** 5 files that had been byte-scrubbed.



**Resolution:** Applied a targeted regex to strip leading dashes from each affected file:



```powershell

$text = $text -replace '^-+', ''

```



This removed the spurious `---` prefix while preserving all legitimate hyphens in the rest of the file.



**Lesson:** When byte-scrubbing multi-byte UTF-8 characters, a single non-ASCII character can become multiple hyphens. If those hyphens land at the start of a file, they trigger frontmatter parsing in modern Rust compilers.

### Problem 4: Missing Trait Imports in commands.rs



**Symptom:**



```text

error[E0599]: no method named `find_by_document_id` found

&#x20;             for struct `SqliteAttachmentRepository`



error[E0599]: no method named `delete` found

&#x20;             for struct `LocalAttachmentStorage`

```



**Root Cause:** The `commands.rs` file used `SqliteAttachmentRepository` and `LocalAttachmentStorage` structs directly, calling methods defined on traits (`AttachmentRepository` and `AttachmentStorage`). The traits themselves were not imported into scope. In Rust, trait methods are only callable when the trait is in scope via a `use` statement.



**Resolution:** Added two missing imports:



```rust

use crate::domain::attachment::AttachmentRepository;

use crate::infrastructure::attachment_storage::AttachmentStorage;

```



**Lesson:** In Rust, using a concrete type that implements a trait does not automatically bring the trait methods into scope. The trait must be explicitly imported wherever its methods are called.

### Problem 5: TypeScript Type Error for Tauri Dialog Plugin



**Symptom:**



```text

error TS2339: Property 'path' does not exist on type 'never'.

&#x20; selected.path

```



**Root Cause:** The `open()` function from `@tauri-apps/plugin-dialog` in Tauri v2 returns `string | null` when `multiple: false`. The code assumed it returned an object with a `.path` property (which was the Tauri v1 API shape). TypeScript inferred `never` for the else branch of a redundant type guard.



**Resolution:** Simplified the assignment:



```typescript

const filePath = selected;

```



No conditional branch needed because the type is already `string` after the null guard.



**Lesson:** Always check the actual TypeScript type definitions of Tauri plugin packages rather than assuming API shape from documentation or Tauri v1 patterns.

### Problem 6: Files Opened as Garbage Text in Notepad



**Symptom:** When clicking "Open" on an attached PDF, Windows opened the file in Notepad, displaying raw binary data as garbled text.



**Root Cause:** The stored filename used a `.bin` extension:



```text

27659926-a1f4-40b6-acb7-c71ad2b4bbfc.bin

```



When `tauri_plugin_opener::open_path()` asked Windows to open this file, Windows looked at the `.bin` extension, found no associated application, and fell back to Notepad.



**Resolution:** Changed the domain entity to derive the stored filename extension from the validated MIME type instead of using `.bin`:



```rust

let extension = match mime_type.as_str() {

&#x20;   "application/pdf" => "pdf",

&#x20;   "image/jpeg"      => "jpg",

&#x20;   "image/png"       => "png",

&#x20;   "image/webp"      => "webp",

&#x20;   _                 => "bin",

};

let stored_filename = format!("{}.{}", Uuid::new_v4(), extension);

```



This produces filenames like `bc5c80db-8160-416d-93b5-606cf8db6318.pdf`. Windows now sees the correct extension and launches the correct default application.



**Security note:** The extension is derived from the already-validated MIME type, not from any user input. The filename remains a UUID. There is no path traversal risk.



**Test impact:** The original `stored_filename_ends_with_bin` test was replaced with four specific tests, one for each supported MIME type. Test count went from 142 to 145.



**Lesson:** When the OS file opener relies on extension-based dispatch (which Windows does), the stored filename must carry the correct extension. Using `.bin` for everything is safe from a naming perspective but breaks the user experience on open.

### Problem 7: Capabilities File Not Actually Written



**Symptom:** After running `Set-Content` to fix the capabilities file, the build produced the same error. Reading the file confirmed the old content was still present.



**Root Cause:** PowerShell's `Set-Content` command silently failed or the updated command was not actually executed (the previous command block's error interrupted the pipeline).



**Resolution:** Used `[System.IO.File]::WriteAllText()` with an explicit `Resolve-Path` call to write the file, followed by an immediate `Get-Content` verification.



**Lesson:** When writing files from PowerShell in a multi-command pipeline, always verify the file contents after writing. The safest approach is to use `[System.IO.File]::WriteAllText()` as a standalone statement.



---



### Problem 8: cargo fmt Differences



**Symptom:** `cargo fmt --check` returned exit code 1 with extensive formatting diffs across all new files.



**Root Cause:** The files were written from PowerShell with manually formatted Rust code that did not match `rustfmt`'s style rules exactly (column-aligned match arms, method chain formatting, trailing newlines, module declaration ordering).



**Resolution:** Ran `cargo fmt` to auto-format all files. No manual intervention required. The diffs were purely cosmetic — no logic changes.



**Lesson:** When writing Rust files from an external tool, always run `cargo fmt` before checking in. Manual formatting will never match `rustfmt` exactly.

## 6. Design Decisions and Rationale



| Decision | Rationale |

|---|---|

| Separate `attachments` table instead of extending `documents` | Preserves existing schema. Allows future multi-attachment support without migration. ON DELETE CASCADE handles cleanup automatically. |

| `file_path` column left in place | Removing it requires a SQLite migration (ALTER TABLE limitations). The column is harmless as a nullable legacy field. Formal deprecation in a later sprint. |

| UUID stored filename with validated extension | Prevents filename collisions and path traversal. Extension enables correct OS file association. MIME type remains authoritative. |

| `AttachmentStorage` trait | Decouples application logic from filesystem operations. Enables future replacement with SQLite BLOB storage, encrypted storage, or cloud storage without changing use cases. |

| Physical file deleted AFTER metadata commit | Safe replacement sequence: if the new file fails to persist metadata, the old file is still intact. An orphaned new file is cleaned up. An orphaned old file (if cleanup fails) is acceptable — the new attachment is live. |

| One attachment per document in UI, many allowed by schema | Schema has no UNIQUE constraint on `document_id`. UI currently manages one attachment. Future sprint can add multi-attachment without migration. |

| Attachment state lives in `DocumentList.tsx` | Avoids redesigning App.tsx state management. Attachment data is document-adjacent UI state. Acceptable for v0.7.0 scope. Can be lifted upward in a later sprint if needed. |

| `open()` import directly in `DocumentList.tsx` | Minor architectural impurity. The file picker call could be behind `documentService.ts` or a `filePickerService.ts`. Acceptable for v0.7.0. Recommended cleanup for v0.8.0. |

## 11. Conclusion



Sanchaya v0.7.0 successfully transforms the application from a metadata tracker into an artifact vault. The implementation extends the existing clean architecture without introducing new frameworks, patterns, or dependencies beyond what was strictly necessary. Every existing feature continues to work. The test count nearly doubled. The eight problems encountered during implementation — encoding issues, capability naming, type mismatches, and the file extension oversight — were all resolved surgically without redesigning any working component.



The attachment architecture is intentionally built as a foundation. The `AttachmentStorage` trait, the separate `attachments` table, and the domain-level MIME validation create extension points for encrypted storage, multi-attachment support, SQLite BLOB storage, and cloud sync — none of which need to be built now, but all of which can be built later without breaking what exists today.
