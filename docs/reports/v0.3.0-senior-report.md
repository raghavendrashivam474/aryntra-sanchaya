**Design Decision — `UpdateDocumentFields` struct:**

The initial implementation passed 7 individual field arguments to `Document::update()`, making 8 total including `&mut self`. Clippy flagged `too_many_arguments` (default limit is 7). Rather than suppressing the lint with `#[allow(clippy::too_many_arguments)]`, we introduced `UpdateDocumentFields` as a dedicated struct that groups the editable fields. This is the better engineering choice because:

1. It makes the update signature self-documenting.
2. It clearly separates "what can be updated" from "what cannot."
3. It scales cleanly when new editable fields are added in future sprints.
4. It allows the struct to be reused at call sites without repetition.

**Design Decision — `FromStr` trait:**

The original `DocumentCategory::from_str()` was an inherent method. Clippy flagged `should_implement_trait` because the method name collides with the standard library trait `std::str::FromStr`. Instead of renaming the method (which would break every call site) or suppressing (which hides a real design flaw), we implemented the standard trait directly:

```rust
impl FromStr for DocumentCategory {
    type Err = ();

    fn from_str(s: &str) -> std::result::Result<Self, Self::Err> {
        match s {
            "identity" => Ok(DocumentCategory::Identity),
            // ... other variants
            _ => Ok(DocumentCategory::Other),
        }
    }
}
This means DocumentCategory now works with:

"identity".parse::<DocumentCategory>()
Standard Rust string parsing idioms
Any generic code that expects FromStr
The Err type is () because parsing never truly fails — unknown strings map to Other. This is a deliberate domain rule.

5. Problems Encountered and Resolutions
5.1 Trait Extension Compilation Cascade
Problem:

Adding update() to the DocumentRepository trait immediately broke compilation of every file that implements the trait — including fake repositories in two existing test modules.

text

error[E0046]: not all trait items implemented, missing: `update`
Three implementations needed updating:

SqliteDocumentRepository (infrastructure)
FakeDocumentRepository in add_document.rs tests
FakeDocumentRepository in list_documents.rs tests
Resolution:

We updated all three implementations in a single step rather than using a partial approach. Every fake repository received a complete update() implementation that mirrors real behavior:

Rust

fn update(&self, document: &Document) -> Result<()> {
    let mut docs = self.documents.borrow_mut();
    if let Some(existing) = docs.iter_mut().find(|d| d.id == document.id) {
        *existing = document.clone();
        Ok(())
    } else {
        Err(SanchayaError::NotFound(document.id.clone()))
    }
}
Lesson: When extending a trait, the cost of the change is proportional to the number of implementors. This is expected behavior in Rust. The compiler forces completeness, which is a feature — it guarantees every implementation handles the new capability. In a larger codebase, this argues for careful consideration before adding trait methods, but here the cost was acceptable and the compiler caught every site.

5.2 Clippy: should_implement_trait on from_str
Problem:

text

error: method `from_str` can be confused for the standard trait method
       `std::str::FromStr::from_str`
The existing DocumentCategory::from_str() was an inherent method with the same name as the standard library trait method.

Resolution:

Implemented the actual std::str::FromStr trait rather than suppressing the lint. This required changing every call site from DocumentCategory::from_str(&s) to s.parse::<DocumentCategory>().unwrap_or(DocumentCategory::Other).

Why not suppress?

Suppressing clippy with #[allow(clippy::should_implement_trait)] would have been faster but would have:

Hidden a genuine API design issue.
Made DocumentCategory incompatible with generic parsing contexts.
Violated the established quality gate (-D warnings).
The fix was more work but the right engineering decision.

5.3 Clippy: too_many_arguments on Document::update()
Problem:

text

error: this function has too many arguments (8/7)
Document::update() initially took &mut self plus 7 field arguments, totaling 8. Clippy's default limit is 7.

Resolution:

Introduced UpdateDocumentFields struct to group the editable fields:

Rust

pub struct UpdateDocumentFields {
    pub title: String,
    pub category: DocumentCategory,
    pub description: Option<String>,
    pub file_path: Option<String>,
    pub issuer: Option<String>,
    pub issue_date: Option<DateTime<Utc>>,
    pub expiry_date: Option<DateTime<Utc>>,
}
The update method signature became:

Rust

pub fn update(&mut self, fields: UpdateDocumentFields) -> Result<()>
Why not suppress?

#[allow(clippy::too_many_arguments)] was considered but rejected. The struct approach is genuinely better:

Self-documenting at call sites.
Clear contract about what is editable.
Extensible without signature changes.
Enables struct update syntax (..default_fields) in tests.
Trade-off: Document::new() also has 7 arguments (at the limit). We did NOT refactor new() in this sprint because the brief explicitly says "do not refactor unrelated code." If a future sprint adds a field to Document, new() will also need a builder or struct pattern. That's a known future cost.

5.4 Windows Linker File Lock (LNK1104)
Problem:

text

LINK : fatal error LNK1104: cannot open file
'...\target\debug\deps\app_lib-6829675be55b15a2.exe'
This occurred twice during the sprint. Windows holds file locks on executables that are still in use. A previous cargo test run left the test binary locked, preventing the linker from overwriting it.

Resolution:

PowerShell

# Kill any lingering processes
Get-Process | Where-Object {
    $_.Name -like "*sanchaya*" -or $_.Name -like "*app_lib*"
} | Stop-Process -Force -ErrorAction SilentlyContinue

# Remove the locked file directly
Remove-Item -Path "target\debug\deps\app_lib-*.exe" -Force -ErrorAction SilentlyContinue
Remove-Item -Path "target\debug\deps\sanchaya-*.exe" -Force -ErrorAction SilentlyContinue
Root Cause: Windows does not allow overwriting an executable that another process has open. This is a platform behavior, not a project issue. On Linux/macOS this error does not occur.

Recommendation for future sprints: If this becomes a recurring friction point, consider adding a pre-test.ps1 script that cleans stale binaries before running tests. Alternatively, cargo clean resolves it but is slower because it forces a full rebuild.

5.5 Unused Import After Refactoring
Problem:

After introducing UpdateDocumentFields and restructuring the domain, clippy reported:

text

error: unused import: `UpdateDocumentFields`
  --> src\infrastructure\document_repository.rs:11
The production code in document_repository.rs does not use UpdateDocumentFields — only the test module does. However, the import was at the file level, making clippy flag it.

The application test module also had a redundant re-import of UpdateDocumentFields since use super::* already brings it into scope.

Resolution:

Infrastructure: Moved UpdateDocumentFields import from the production-level use block into the test module's own use block.
Application tests: Removed redundant import since use super::* covers it.
Rust

// Infrastructure production imports (clean)
use crate::domain::document::{Document, DocumentCategory, DocumentRepository};

// Infrastructure test imports
#[cfg(test)]
mod tests {
    use super::*;
    use crate::domain::document::{DocumentCategory, UpdateDocumentFields};
}
Lesson: use super::* in test modules only imports items from the parent module's namespace, not transitive re-exports. When moving imports between production and test scopes, you must explicitly import types that the production code doesn't re-export.

5.6 cargo fmt Formatting Divergence
Problem:

The files were written with manual formatting that cargo fmt wanted to rewrite. This showed up as extensive diffs in cargo fmt --check, including:

Import sorting (alphabetical)
Line wrapping for long method chains
Trailing newlines on module files
Argument formatting in function calls
Resolution:

Applied cargo fmt directly rather than fighting individual formatting differences. All subsequent edits were made with awareness that fmt would reformat, and we ran cargo fmt as a final step.

Lesson: Run cargo fmt immediately after writing each file rather than accumulating formatting drift. This sprint initially wrote files with one style, then had to reconcile with fmt. A better workflow: write the file, run cargo fmt, verify with --check, commit.

10. Known Limitations and Future Considerations
10.1 Document::new() Argument Count
Document::new() currently takes 7 arguments (at clippy's limit). If a future sprint adds a field to the Document entity, new() will need a CreateDocumentFields struct or a builder pattern to stay within the lint threshold. This is a known cost deferred to when it becomes necessary.

10.2 Duplicate Fake Repositories
There are now three independent FakeDocumentRepository implementations across the application test modules (add_document, list_documents, update_document). They are nearly identical. A future cleanup sprint could extract a shared test utility, but the brief explicitly stated "do not refactor unrelated code," so this was left as-is.

10.3 Delete UI Not Yet Implemented
The repository and infrastructure already support delete(). The application and presentation layers do not yet expose it, and the frontend has no delete button. This is a natural candidate for v0.4.0.

10.4 No Optimistic Concurrency
The update path does not check whether the document was modified between the find_by_id() and update() calls. In a single-user desktop application this is acceptable. If Sanchaya ever supports concurrent access (e.g., multiple windows, cloud sync), optimistic concurrency via a version field or updated_at comparison would be needed.
