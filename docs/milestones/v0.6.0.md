## What Was Built

### Domain — Rust

Added ExpiryStatus enum to domain/document.rs:

    NoExpiry      expiry_date is None
    Expired       expiry_date < now
    ExpiringSoon  now <= expiry_date <= now + 30 days
    Valid         expiry_date > now + 30 days

Added Document::expiry_status(now: DateTime<Utc>) -> ExpiryStatus.

"now" is injected as a parameter. The domain never calls Utc::now()
for classification. This makes every boundary condition testable with
a deterministic timestamp.

Added EXPIRY_SOON_THRESHOLD_DAYS = 30 as the single source of truth
for the 30-day threshold on the Rust side.

ExpiryStatus serializes with serde rename_all = "snake_case":
  no_expiry, expired, expiring_soon, valid

### Domain Tests

10 new tests added. All boundary conditions are explicitly covered:

  expiry_date = None             -> NoExpiry
  expiry_date = yesterday        -> Expired
  expiry_date = well in past     -> Expired
  expiry_date = exactly now      -> ExpiringSoon
  expiry_date = now + 1 day      -> ExpiringSoon
  expiry_date = now + 30 days    -> ExpiringSoon
  expiry_date = now + 31 days    -> Valid
  expiry_date = far future       -> Valid
  threshold constant = 30        -> verified
  serialization of all variants  -> verified

### Frontend — TypeScript

Added to types/document.ts:

  ExpiryStatus type mirroring Rust enum
  EXPIRY_SOON_THRESHOLD_DAYS = 30 (frontend single source of truth)
  EXPIRY_STATUS_LABELS for display

  getExpiryStatus(expiryDate, now)    pure function, mirrors Rust

## Architecture Decisions

### Why expiry classification lives in Domain

ExpiryStatus is a business concept, not a visual one. The domain
owns the rules. The frontend mirrors them in a pure function using
the same threshold constant independently. Neither calls the other.

### Why "now" is a parameter

Document::expiry_status(now) accepts the timestamp as an argument.
This makes the method deterministic in tests. Production callers
pass Utc::now(). The domain itself never decides what "now" is.

### Why no new Tauri command was needed

The frontend already receives expiry_date on every Document from
list_documents. ExpiryStatus is derived client-side from that field
using getExpiryStatus(). This is the same pattern as category
filtering in v0.5.x — no round-trip to the backend required.

### Why the expiry summary reflects the full vault

expirySummary is computed from documents (the full list), not
filteredDocuments. This means the counts always show the true
state of the vault. A user filtering by "Expiring Soon" still
sees that there are also 2 expired documents needing attention.
